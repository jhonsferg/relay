## [Unreleased]

### Added

- `benchmarks/memory/nativehttp_test.go`: `BenchmarkMemory_VsNetHTTP_*` pairs relay against a bare `net/http.Client` against the same local server, so `-benchmem` output is directly comparable. Added as a regression gate for the memory-overhead fixes below, and to make future relay-vs-net/http comparisons reproducible in-repo instead of ad hoc.
- More relay-vs-net/http benchmark pairs, filling gaps identified by a coverage audit: `BenchmarkMemory_VsNetHTTP_{Relay,Native}_Redirect3Hop` (3-hop redirect chain), `BenchmarkMemory_VsNetHTTP_{Relay,Native}_ManyHeaders` (40 request headers), `BenchmarkMemory_VsNetHTTP_Relay_GET_NoTiming` (the allocation floor with `WithDisableTiming` - superseded later this round by timing becoming opt-in by default, see below), `BenchmarkLargeStream_Sequential_Standard` (net/http counterpart to the existing ~35MB streaming benchmark), and `BenchmarkConcurrency_ParallelRequests_Native` (net/http counterpart to relay's existing sustained-parallel-load benchmark, confirming relay's bulkhead/pool/circuit-breaker checks don't add contention overhead beyond net/http's own). **Correction**: this entry originally claimed `BenchmarkLargeStream_Sequential_Relay` showed relay ~6x cheaper than `net/http` at ~35MB. That comparison was invalid - see the "Fixed" entry below for `benchmarks/bigdata` for what was actually being measured.
- `benchmarks/common/execute_test.go`: `BenchmarkExecute_ResilienceIdle_{RetryEnabled,CircuitBreakerEnabled,HedgingEnabled}` isolate the "opt-in tax" of enabling retry/circuit-breaker/hedging when they never actually trigger (the common steady-state case for a healthy service), as opposed to the existing `BenchmarkExecute_WithRetry`, which measures the cost when retry actually fires. Result: retry and circuit-breaker are statistically free when idle; hedging costs a real, now-quantified ~11 extra allocations per request even when the hedge attempt never launches.
- Exhaustive tests closing coverage gaps identified by a repo-wide audit, focused on packages with real logic and near-zero coverage rather than raw line-count: `schema.go` (JSON Schema/struct-tag validation - `toFloat64`/`toNumber`/`checkJSONType` were previously untested in isolation, at 0-50% coverage; now ~100% including every numeric-kind branch of `applyRule`, malformed `min=`/`max=` rules, nested `properties`, nested/`pattern`/`minLength`/`maxLength`/`minimum`/`maximum` JSON Schema keywords, and an invalid regex pattern), `har.go` (`ExportHAR`, `All`, and `Middleware` were entirely untested - 0% - despite `WithHARRecording`'s own code path bypassing all three; now covered end-to-end, plus the `RoundTrip` transport-error branch and `buildHARRequest`'s no-body branch), `cache.go`'s `evict` (was 44% - now covers expired-entries-preferred-over-oldest eviction, `insertOrder` compaction correctness across multiple eviction rounds, and a concurrent `Set`/`evict` stress test asserting the store never exceeds capacity), and `dns_cache.go`'s `DialContext` (was 21% - the existing tests only ever exercised the IP-literal bypass since the mock server's URL host is an IP; a new test targets `http://localhost:<port>` to exercise the real DNS-resolution-then-dial-loop path). Also added focused smoke tests for previously 0%-covered option constructors/getters that turned out to be genuinely untested rather than platform-excluded: `WithClientCert` (file-based, `WithClientCertPEM`'s sibling), `WithRequestSigner` (confirms the `WithSigner` alias actually wires through), `Request.Context()`, and `WithDNSOverride` (confirms the override actually redirects the dial, not just that it populates config).
- `resilience_combined_test.go`: a combined-stack smoke/interaction test running retry, circuit breaker, hedging, rate limiting, and a small bulkhead simultaneously under concurrent load with per-request cancellations, asserting nothing panics/deadlocks and the circuit breaker recovers rather than getting stuck. This class of test - several resilience features interacting under real concurrent contention - is exactly where bugs like the circuit-breaker half-open probe-slot leak (fixed separately, see below) are found; this test doesn't reliably reproduce that specific race (too narrow an interleaving to hit under realistic timing - see `TestCircuitBreaker_AbandonedHalfOpenProbeDoesNotStickForever` for the deterministic regression test for that), but closes the gap of having no interaction-level coverage at all.
- `WithTiming()`: opt-in per-request timing instrumentation, replacing the now-deprecated `WithDisableTiming()` (kept as a no-op for source compatibility). See "Changed" below for the default-behavior flip this pairs with.
- `WithDisableRedirectTracking()`: opt-out of populating `Response.RedirectCount`/`RedirectChain`, skipping the per-request `redirectState` pool round-trip and `context.WithValue` allocation for callers who don't read either field. `WithMaxRedirects` enforcement and `WithBeforeRedirectHook` are unaffected. Redirect tracking itself stays on by default - no behavior change unless you opt out.
- `Extension` interface and `WithExtension()`: a new, additive registration seam for building relay extensions - bundles transport middleware, hooks, and construction-time config validation into one unit (`Apply(cfg *Config) error`), instead of hand-wiring `WithTransportMiddleware` plus assorted hook options. An `Apply` error is logged via `Config.Logger`, not fatal, matching the existing TLS-pinning error-handling precedent. No existing `ext/*` package has been migrated onto this yet - it's available for new extensions.
- Docker-backed integration tests for the three `ext/*` packages whose existing tests only ever exercised an in-process fake, never the real backend: `ext/redis` and `ext/ratelimit/distributed` (both previously tested exclusively against `miniredis`, an in-memory Redis simulator - the sliding-window rate limiter's atomic Lua script is exactly the kind of behavior a simulator's own Lua interpreter can't guarantee bug-for-bug identical to real Redis) and `ext/memcached` (previously tested against a hand-rolled fake that wasn't even a real memcached protocol simulator, so its key-encoding/protocol-constraint logic was never exercised against the real wire format). New `*_docker_test.go` files in each package spin up real `redis:7-alpine`/`memcached:1.6-alpine` containers via `github.com/testcontainers/testcontainers-go` (a new dependency, added only to these three modules' `go.mod`), gated behind a new `//go:build docker` tag so they're opt-in and require a local Docker daemon - normal `go test ./...` is unaffected. **Local-only, by design**: run via `go test -tags=docker ./...` from within each module directory on a machine with Docker; these are deliberately not wired into any GitHub Actions workflow and must not be added to CI.
- `ext/http3`'s first functional HTTP/3 request/response test (`http3_functional_test.go`, `TestHTTP3_RealRequestRoundTrip`) - every existing test in the package only asserted that `Transport()`/`WithHTTP3()` didn't panic and returned non-nil; zero real HTTP/3 requests were ever made. The new test spins up a real in-process `quic-go/http3.Server` (self-signed cert, real UDP socket) and drives a real relay client through `WithHTTP3Config` against it, asserting the response round-trips correctly and `resp.Raw().ProtoMajor == 3`.
- Docker-backed integration tests (build tag `docker`, see above) for three more packages, at the user's specific request to verify against real identity providers and a real cloud-API-compatible server rather than relying solely on the existing httptest-based coverage: `ext/oauth` and `ext/oidc` now additionally test their client-credentials flows against a real **Keycloak** container (a pre-seeded realm/confidential-client imported at container startup), including a negative test confirming a wrong client secret is genuinely rejected by Keycloak, not just accepted by construction. `ext/sigv4` now additionally signs a real request against a **MinIO** container (a genuine S3-API-compatible server that strictly validates AWS SigV4 signatures) - proving the signature relay produces is cryptographically correct, with a paired negative test (wrong secret key rejected) confirming MinIO is actually validating and not accepting anything. A real AWS-hosted S3 bucket or LocalStack was considered for the sigv4 case instead of MinIO, but LocalStack's `latest` image now requires a paid license/auth token even for its community S3 service, and a real AWS account is out of scope for a credential-free automated test suite; MinIO needs neither and is fully open source.

### Added

- `pagination_test.go`: `pagination.go` had no test file at all before this round; added coverage for `Paginate`/`PaginateWith` including the header/query-preservation-across-pages regression test below and basic Link-header termination.
- `resilience_combined_test.go`'s sibling additions this round: `TestPriorityQueue_ConcurrentMidQueueCancellations` and `TestSRVResolver_CoalescesConcurrentMisses`/`TestSRVResolver_DetachesLeaderContext` stress the same class of "several features interacting under real concurrent contention" gap identified last round, scoped to the priority queue and SRV discovery specifically.

### Added (perf)

- `BenchmarkRetryBudget_CanRetry_SustainedTraffic`, `BenchmarkJSONSchemaValidator_Pattern`, `BenchmarkPriorityQueue_RemoveItem_LargeQueue`: added alongside the three algorithmic fixes below to make the improvement (and any future regression) directly measurable. Measured impact: `retryBudgetTracker.CanRetry` 0 B/op, O(1) regardless of window size (previously O(entries in window)); `JSONSchemaValidator`'s `pattern` keyword ~13.5x faster and allocation-free after the first use (5364 ns/op, 66 allocs/op → 398 ns/op, 0 allocs/op); `priorityQueue.removeItem` on a 10,000-item queue ~24x faster (2407 ns/op → 102 ns/op).

### Fixed

- `fix(docs)`: `Config.AutoIdempotencyOnSafeRetries`'s and `WithAutoIdempotencyOnSafeRetries`'s own doc comments in `config.go` said "POST, PATCH, and DELETE are skipped" - backwards from the actual, tested behavior (`isSafeMethod` in `idempotency.go`, confirmed by `TestWithAutoIdempotencyOnSafeRetries_DELETE_GetsKey`): DELETE **is** included (it's idempotent per RFC 9110 §9.2.2, same as GET/HEAD/PUT/OPTIONS/TRACE); only POST and PATCH are skipped. Corrected both comments to match the real, already-correct code.
- `fix(docs)`: `docs/reference/config.md` was severely out of sync with the actual public API - a comparison against every real `With*` `relay.Option` function in the code turned up **9 fully fabricated functions with no corresponding code** (`WithAPIKey`, `WithBasicAuth`, `WithBearerToken`, `WithContentTypeDecoder`, `WithContentTypeEncoder`, `WithDisableRedirect`, `WithHMACSign`, `WithOAuth2`, `WithTransport`), several documented signatures that didn't match the real ones at all (e.g. `WithRateLimit(config *RateLimitConfig)` vs. the actual `WithRateLimit(rps float64, burst int)`; `WithRetry`'s documented `RetryConfig` fields `WaitMin`/`WaitMax`/`RetryOn` don't exist - the real fields are `InitialInterval`/`MaxInterval`/`RetryIf`), a final "Complete Configuration Example" that called `client.Execute(context.Background(), client.Get(...))` when `Client.Execute` takes no context parameter at all, and dozens of real, existing options with no documentation entry. Rewrote the file from scratch against the actual `config.go` (plus `compress.go`, `credentials.go`, `logging_middleware.go`, `push.go`, `signer.go`, `srv_discovery.go`, `tls.go`, `tls_watcher.go`, `unix_transport.go`) source - every one of the ~76 real `With*` client options now has its own entry with the real signature, struct fields, and defaults; every example was checked against the real method/type names it references (`Client.Config()`, `Response.IsTruncated()`, `PutResponse`, `NewInMemoryCacheStore`, etc.), and the final example is a genuinely compilable program (its original version was missing a `net/http` import once the signature was corrected). Added a short "Per-request authentication (not client options)" section clarifying that `WithAPIKey`/`WithBasicAuth`/`WithBearerToken` are real - but as `*Request` builder methods (`req.WithBearerToken(...)`), not `relay.Option` functions - which is almost certainly the confusion that produced the fabricated `relay.With*` versions in the first place.
- `fix(core)` **(data corruption)**: `coalesceTransport.RoundTrip` (`coalesce.go`, `WithRequestCoalescing`) gave every concurrently-coalesced caller the exact same `http.Header` map instead of an independent copy each. `cloned := *r.resp` only shallow-copies the `http.Response` struct - `cloned.Header` still aliased the one map `singleflight.Do` produced for the shared underlying request, which then flows straight into each caller's own `Response.Headers` via `newResponse`'s `r.Headers = resp.Header`. `Response.Headers` is a plain, exported `http.Header` with public `Set`/`Add`/`Del` methods that relay never disallows calling, so any one caller mutating its own response's headers silently corrupted every other caller's headers that happened to be coalesced onto the same request - a real footgun for anything that annotates or strips headers on the response it received, believing it owned that map exclusively. The sibling dedup path, `deduplicator.RoundTrip` in `singleflight.go` (`WithRequestDeduplication`), already gets this right - it explicitly does `Header: r.header.Clone()` per caller - making `coalesceTransport`'s missing clone an inconsistency within the same codebase, not just an isolated oversight. New regression test `TestCoalesce_ResponseHeadersNotSharedAcrossCallers` confirmed against the pre-fix code deterministically (5/5 runs: caller 1 always observed caller 0's `Headers.Set` call) and now passes. Fixed by cloning the header map per caller (`cloned.Header = r.resp.Header.Clone()`), mirroring the pattern `deduplicator.RoundTrip` already established.
- `fix(core)` **(data corruption)**: `harTransport.RoundTrip` (`har.go`) truncated the *actual response delivered to the caller* to 10 MB whenever `WithHARRecording` was enabled and the server sent a larger body - the same-shaped bug as the request-body truncation fixed for `buildHARRequest` earlier this round (see the "nine bugs" entry below), but left present on the response side. `RoundTrip` read `resp.Body` through `io.LimitReader(resp.Body, maxHARRespBodySize)` and then reassigned `resp.Body = io.NopCloser(newBytesReader(body))` using that same capped byte slice both for the HAR recording *and* for the response object `Client.Execute` actually buffers and returns - so any response over 10 MB was silently cut to exactly 10 MB for every caller, not just the recorded copy, whenever a `HARRecorder` was attached. New regression test `TestHARRecorder_LargeResponseBodyDeliveredInFullNotTruncated` confirmed against the pre-fix code (an 11 MB response arrived at the caller as exactly 10485760 bytes) and now passes. Fixed the same way the request side already was: read `resp.Body` unbounded via plain `io.ReadAll`, reassign the full, untruncated body back onto `resp.Body`, and only cap what's stored in the HAR entry's `Response.Content.Text` - `Response.BodySize` and `Response.Content.Size` now always reflect the true full size (mirroring `HARRequest.BodySize`'s existing contract), so a HAR consumer can tell a body was recording-truncated by comparing `BodySize` against `len(Content.Text)`, same as the request side already documents.
- `fix(core)`: `(*Client).With` shared `WithDynamicTLSCert`'s `CertWatcher` "exclusive ownership" across parent and child clients instead of transferring or dropping it. `WithDynamicTLSCert`'s own doc comment states the watcher is "exclusively owned by this client (nothing else can reach it)", which is exactly why `Client.Shutdown` stops it unconditionally when `ownsCertWatcher` is true - but `Config.clone()` (used by `With`) copies both the `*CertWatcher` pointer and `ownsCertWatcher=true` verbatim via its initial `c := *cfg` shallow copy, so after one `With` call *two* `*Client` values reach the same watcher, both believing they exclusively own it. Calling `Shutdown` on either one - most plausibly the short-lived child, e.g. a per-request or per-tenant client built via `With` and shut down when done - silently stops the shared background reload goroutine out from under the other, still-live client, which then keeps serving an increasingly stale certificate with no error or other indication anything broke. New regression test `TestClient_With_DoesNotShareCertWatcherOwnership` confirmed against the pre-fix code (child's `Shutdown` closed the parent's `stopCh`, exactly as predicted) and now passes; the existing `TestClient_Shutdown_StopsOwnedCertWatcher` (no `With` involved) confirms the original, never-cloned owner still stops its own watcher correctly. Fixed by clearing `ownsCertWatcher` in `clone()` - a cloned config's watcher is treated the same way `WithCertWatcher`'s caller-supplied watcher already is (shared, not auto-stopped by `Shutdown`); only the original client that actually called `WithDynamicTLSCert` remains the owner.
- `fix(core)`: `(*Client).With` re-ran every previously-registered `Extension`'s `Apply` on each call, instead of only newly-added ones. `Config.clone()` (used by `With`) copies both `cfg.extensions` and the `TransportMiddlewares`/hooks that applying those extensions already produced on the parent; `buildClient`'s extensions loop then iterated the *entire* cloned `cfg.extensions` slice again, calling `Apply` a second time on a config that already reflected the first application. For an `Apply` that appends middleware or hooks - the exact pattern the `Extension` interface's own doc comment and `TestWithExtension_ApplyRuns` describe - this duplicated the effect on every `With` call: one registered extension became 2 applications (and 2x its middleware/hooks) after a single `With`, 3x after two chained `With` calls, and so on, compounding indefinitely for long-lived clients that build variants via repeated `With`. New regression test `TestWithExtension_NotReappliedOnWith` confirmed against the pre-fix code (`applyCount` and registered-middleware count both came back 2 after one `With` call, exactly as predicted) and now passes, including chained `With` calls and adding a second extension to a child client. Fixed by tracking how many leading entries of `cfg.extensions` have already been applied (`Config.appliedExtensions`, carried forward by `clone()`) and only applying the tail past that count in `buildClient`.
- `fix(core)` **(data corruption)**: `timing.go` pooled a single `(*timingCollector, *httptrace.ClientTrace)` pair via `sync.Pool` and reused it across unrelated requests. The trace's closures close over the collector by reference, and `net/http`'s `dialParallel` can fire a callback (e.g. `ConnectDone`) from a "loser" dial goroutine (IPv4/IPv6 happy eyeballs, or any race between concurrent dial attempts) *after* the request that raced it has already completed and returned its collector to the pool - that late, unrelated callback silently wrote into whichever *different* request had since been leased the same reused object, corrupting its `Response.Timing` with a foreign timestamp. Confirmed reproducible with a deterministic test (no real network race needed): lease request A, return A's collector, lease request B (pool reuses the same object), fire A's now-stale callback directly, observe B's field corrupted - the test fails against the pre-fix code and passes against the fix. Fixed by allocating a fresh collector and trace per request instead of pooling them (only when `WithTiming`/`WithAdaptiveTimeout` is enabled, so unaffected clients pay nothing) - a stale callback can now only ever write into the collector it was originally built for, which nothing else references once that request is done. Measured cost: ~9 more allocations per request with timing enabled (93 → 102 allocs/op) in exchange for making this class of cross-request corruption structurally impossible.
- `fix(core)`: nine bugs found via a systematic file-by-file bug-hunt of the root module (mirroring the same pass already done across all `ext/*`), each with a regression test confirmed to fail on the pre-fix code and pass with it:
  - **`cache.go`** (`inMemoryCacheStore`): `Delete` and `Get`'s lazy-expiration path removed a key from `entries` but never from `insertOrder`, leaving a stale reference. Re-`Set`-ing the same key later looked like a brand-new key (a duplicate reference got appended), so the next eviction could pop the stale first reference and delete the just-re-inserted *live* entry instead of the genuinely oldest one - violating the documented oldest-first eviction policy - and, independently, left `insertOrder` growing unboundedly for any Delete/Get-driven churn that never triggers `evict()`. Fixed with a new `removeFromInsertOrder` helper called from both paths.
  - **`ratelimit.go`** (`newTokenBucket`): `Burst: 0` (the zero value if a caller forgets to set it) set `maxNanoBurst` to 0, and `refill()` unconditionally clamps `nanoTokens` back down to `maxNanoBurst` on every call - tokens could never reach the 1-token threshold `Wait`/`TryAcquire` require, permanently deadlocking the limiter regardless of `RequestsPerSecond`. Fixed to clamp `burst < 1` to 1, mirroring the existing `ratePerUs < 1` guard in the same function.
  - **`adaptive_timeout.go`** (`newAdaptiveTimeoutTracker`): a non-nil config with `WindowSize` left at its zero value (e.g. a caller sets `Percentile`/`Multiplier` but forgets `WindowSize`) crashed the request goroutine with an integer-divide-by-zero panic in `record()` - `count % WindowSize` once the (zero-capacity) window "fills," which happens on the very first call. `newAdaptiveTimeoutTracker` only ever defaulted a fully-`nil` config, never validated individual fields on a non-nil one. Fixed to fall back to the documented default `WindowSize` when `<= 0`.
  - **`hedging.go`** (`executeHedged`): receiving a *failing* result from an earlier attempt while waiting for the hedge delay returned that error immediately, abandoning every remaining hedge attempt - inconsistent with the final collect loop, which correctly only returns early on success and otherwise keeps waiting. A fast transport-level error (e.g. connection refused) from the first attempt defeated hedging entirely instead of giving the remaining attempts a chance, as the doc comment promises ("the first successful response, or the last error if all fail"). Fixed to only short-circuit-return on success, recording the error and falling through to launch the next attempt otherwise.
  - **`retry.go`** (`retryAfterDelay`): a server-supplied `Retry-After: <seconds>` value large enough (e.g. `9223372040`) overflowed `time.Duration`'s int64 nanosecond range, wrapping to a large *negative* duration - a timer with a negative duration fires immediately, so the client retried instantly instead of backing off as the server explicitly asked. Separately, even non-overflowing large values bypassed `RetryConfig.MaxInterval` entirely (only the exponential-backoff path respected it), letting a server dictate an arbitrarily long wait regardless of the caller's configured ceiling. Fixed by capping the parsed seconds well below the overflow boundary and clamping the final duration (from either the seconds or HTTP-date form) to `MaxInterval` when configured.
  - **`schema.go`** (`validateJSONSchema`): a `properties` entry not listed in `required` was still validated even when entirely absent from the object - `propVal` defaulted to `nil`, and `checkJSONType(nil, ...)` reports type `"null"`, failing with `expected type "string", got "null"` for any optional field simply omitted. This made every typed property effectively mandatory regardless of `required`, contradicting standard JSON Schema semantics. Fixed to skip validation for an absent (not merely `null`-valued) optional property.
  - **`har.go`** (`buildHARRequest`): `maxHARBodySize` (10 MB) was meant to bound only the *recorded* HAR text snapshot, but the same limited reader was also used for the bytes reassigned to `req.Body` - the body that actually goes out over the network. Any request body over 10 MB, through a client with HAR recording enabled, was silently truncated before it ever reached the server (in practice, `net/http`'s transfer writer detects the resulting Content-Length/body-length mismatch and fails the request outright). Fixed to read the full body unbounded (required for correctness regardless) and only cap what's copied into the HAR entry's `postData.text`; `BodySize` always reflects the true full size.
  - **`util.go`** (`isRedirectError`): used a heuristic ("wrapped in `*url.Error` and the underlying error is not a `net.Error`") to guess whether a redirect was stopped by `CheckRedirect`'s own `MaxRedirects` policy, so it could be excluded from circuit-breaker failure accounting. The heuristic is far broader than intended: any non-`net.Error` transport failure reaching that point - e.g. a TLS certificate error (`x509.CertificateInvalidError`/`HostnameError`/`UnknownAuthorityError` implement neither `Timeout()` nor `Temporary()`) - was misclassified as a policy error and its circuit-breaker failure silently dropped. Fixed by wrapping a new sentinel (`errMaxRedirectsExceeded`) into the specific "stopped after N redirects" error and checking for it via `errors.Is`, replacing the heuristic entirely (a `BeforeRedirectHooks`-returned error is no longer exempted either, since it may itself reflect a real downstream problem the hook detected).
  - **`sse.go`** (`ExecuteSSEStream`): the `ctx` parameter was never attached to the outgoing request - the doc comment says "close ctx to stop the stream," and there's a `ctx.Done()` check between `scanner.Scan()` calls, but that only fires *between* reads. For a real long-lived SSE connection idle between events (the whole point of the API), `scanner.Scan()` blocks on the socket `Read()`, governed by whatever context the request already carried (`context.Background()` by default) - cancelling `ctx` did not unblock a pending read at all; the connection stayed open until the server sent more data or dropped it. `sse_fanout.go` had to work around exactly this gap by manually attaching `ctx` to a cloned request before every call. Fixed by attaching `ctx` to a clone inside `ExecuteSSEStream` itself (so callers no longer need to); `sse_fanout.go`'s now-redundant workaround was simplified away.
  - **`resolve.go`** (`ResolveTest`): reimplemented a similar-but-not-identical copy of `build()`'s URL-joining logic (`request.go`), missing the excess-leading-slash normalisation both paths apply - for a path like `"//admin"`, `ResolveTest` reported a different URL than what a real request through the same client would actually send, defeating its stated purpose ("debugging URL resolution issues... understanding which normalisation strategy is used"). Fixed by extracting the real logic into a new shared `resolveBaseAndPath` function, called by both `build()` and `ResolveTest` - they can no longer diverge. Also added `Client.Config()` (a `*Config` copy, safe to mutate independently of the live client), since `ResolveTest`'s own doc example (`relay.New().Config()`) referenced a method that didn't exist anywhere in the package.
- `fix(ext/openapi)`: `validatingTransport.RoundTrip` passed `findReq` (host/scheme rewritten to the spec's declared server, so `router.FindRoute` can match a path when the actual target differs - test servers, proxies, etc.) to `openapi3filter.ValidateRequest`, contradicting an inline comment stating the intent was to validate against the real request. Any validator logic inspecting `Request.Host`/`Scheme` would validate against the spec's server host instead of the real target - confirmed via a white-box test that observes `RequestValidationInput.Request.Host` through a custom `AuthenticationFunc` (the only way to make kin-openapi actually surface it), which fails without the fix and passes with it. Also fixed a body leak: the `io.ReadAll(req.Body)` error path returned without closing `req.Body`, violating `http.RoundTripper`'s always-close contract - fixed to close it on that path.
- `fix(ext/vcr)`: `recordRoundTrip` read the original `req.Body` via `io.ReadAll` but never closed it before replacing it with a `NopCloser`, leaking the underlying resource (e.g. an open file descriptor for a file-backed upload body) on every recorded request - fixed to close it. Also, `headerMapFromHeader` kept only the first value (`v[0]`) for each response/request header before persisting to the cassette, silently discarding the rest of any repeated header (e.g. multiple `Set-Cookie` values). Fixed by changing `RecordedRequest`/`RecordedResponse.Header` from `map[string]string` to `map[string][]string` (matching `http.Header`'s own shape) and adding a custom `UnmarshalJSON` that still reads the older single-value on-disk format for backward compatibility with existing cassette files, mirroring the existing `BodyEncoding` backward-compat pattern in the same file.
- `fix(ext/zap)`: `NewAdapter(nil)` and `NewSugaredAdapter(nil)` panicked (nil pointer dereference calling `Sugar()` on a nil `*zap.Logger`) instead of falling back to a usable default, unlike `ext/slog`'s equivalent constructor which defaults to `slog.Default()`. Fixed to fall back to zap's global logger (`zap.L()`/`zap.S()`), matching that convention.
- `docs(ext/websocket)`: `Conn.Close`'s doc comment claimed it "sends a close frame and then closes the underlying connection immediately," but the implementation (`c.ws.Close()`) is `gorilla/websocket`'s abrupt close, which per its own docs never sends or waits for a close message - the peer sees an abnormal TCP teardown (e.g. close code 1006), not a clean RFC 6455 close. `CloseGracefully` (which does send a close frame and wait for the peer's echo) makes the contrast clear enough that this looks like documentation drift rather than intended behavior needing a code change; fixed the doc to describe the actual (abrupt) behavior. No behavior change.
- `fix(ext/sentry)` **(security)**: `scope.SetRequest(req)` was passing the real, unsanitized `*http.Request` straight to Sentry - reachable via the transport-error path (`CaptureException`), which unlike the 5xx/4xx path (`CaptureEvent(buildEvent(...))`, which builds its own headerless `Request`) lets `scope.ApplyToEvent` populate `Event.Request.Headers`/`Cookies` directly from whatever was passed to `SetRequest`. With a host application's `sentrygo.ClientOptions.SendDefaultPII: true` (e.g. because it wants full PII from other Sentry integrations), `Authorization`/`Cookie`/`X-Api-Key`/etc. headers - and thus credentials - were forwarded to Sentry on every transport-error event. This is the same class of bug documented as fixed earlier in this file, but the fix was absent from the current `sentry.go` (the CHANGELOG entry predates this session and the code apparently regressed or was never actually applied - confirmed by direct code inspection, not assumed). Fixed by cloning the request and stripping `Authorization`, `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-Api-Key` before `SetRequest`, independent of the host's `SendDefaultPII` setting. Regression test (`TestWithSentry_StripsSensitiveHeaders`) confirmed to fail without the fix and pass with it.

- `fix(core)`: `newResponse` (response.go) no longer buffers the response body via `bytes.Buffer.ReadFrom`. Both `bytes.Buffer`'s grow step and a naive `append`-based grow (an intermediate version of this fix) re-copy the *entire* accumulated buffer on every incremental grow; since Go's slice growth factor tapers toward ~1.25x for larger slices rather than a flat 2x, reading a multi-megabyte body in many small `Read` increments summed to several times the final body size in total allocated bytes - confirmed via pprof and an isolated synthetic benchmark against a naive append-based version. `readAllInto` now mirrors the current `io.ReadAll` algorithm instead: independent, exponentially-sized chunks are accumulated and concatenated into one right-sized slice only once, at the end, bringing relay to parity with `io.ReadAll`'s own allocation profile. Fixed to only ever clamp a *known* size hint down to what will actually be read, never invent one. If attempt 1 redirected and then failed with a retryable status, and attempt 2 also redirected before succeeding, the final response's `RedirectChain()` contained hops from both attempts concatenated (reporting a hop from a discarded, failed attempt as if it happened on the successful response), while `RedirectCount` reflected only the last attempt - leaving the two mutually inconsistent.

Profiling `BenchmarkMemory_VsNetHTTP_Relay_GET` (new, see below) showed this accounted for 32% of all memory allocated in the benchmark process. The read now goes directly into `Response.body`'s own backing array (obtained from the pooled `*Response` *before* the read), which grows proportionally to actual body size when the pool misses and self-sizes across reuses when the caller does call `PutResponse()`. `internal/pool/bytespool.go` had no remaining callers after this change and was deleted. All read sites already nil-check `c.circuitBreaker`, so it is now left nil whenever `CircuitBreakerConfig` is nil, matching its documented "Nil when disabled" contract.

Previously spans were created but never propagated downstream, so a service using only `ext/otel` silently broke distributed tracing continuity.

- `go.mod` (core, `ext/otel`, `ext/tracing`): lower the minimum Go version from 1.25.0 to 1.24.0. No code in these modules uses a Go 1.25-only language or stdlib feature; the floor had drifted up via routine dependency-bump commits rather than an actual requirement, needlessly narrowing the pool of consumers who can adopt relay.
- Quick-start docs (`README.md`, `doc.go`): call out that per-request timing (`Response.Timing`) is collected by default and is opt-out via `WithDisableTiming()`, not opt-in — previously this was only documented on the `Config.DisableTiming` field comment. **Superseded by the next entry.**
- **BREAKING (default behavior)**: per-request timing instrumentation (`Response.Timing`, `httptrace`) is now **off by default** instead of on-by-default/opt-out. Enable it explicitly with the new `WithTiming()`. This was the single largest relay-specific per-request allocation cost (~10 allocations) and ran unconditionally even for clients that never read `Response.Timing`. `WithAdaptiveTimeout(...)` automatically forces timing on internally, since it needs latency samples to compute anything - this also fixes a latent bug where `WithDisableTiming()` combined with `WithAdaptiveTimeout(...)` silently starved adaptive timeout of data with no error or warning. relay is pre-v1.0 with no known public importers, so this default flip ships without a deprecation cycle; `WithDisableTiming()` is kept as a documented no-op. **`ext/slog` users**: `ext/slog` reads `Response.Timing.Total` for its `duration_ms` log field - upgrading without adding `relay.WithTiming()` to your client will silently log `duration_ms: 0` on every request. This is not fixed automatically in this release since `ext/slog` itself was intentionally left untouched; add `WithTiming()` to your client construction if you rely on that field.
- CI: benchmarks removed from the automated `Test` pipeline matrix; benchmarks now run on-demand via the separate `Benchmark` workflow. This reduces pipeline duration significantly and avoids false failures caused by infrastructure timing variance.
